# Interaction modalities: keys and checks

Reference date: 2026-11-13. Pattern coverage: all 30 patterns in the existing [APG cache index](skills/accessibility-assessment/knowledge/apg/index.md), plus native HTML. The cache exists; no scraper refresh was needed. This is a checking reference, not a claim that every check is automated.

## 1. Modality definitions and verdicts

| Modality | Input and purpose | Boundary |
|---|---|---|
| `keyboard` | Navigate/activate using **Tab, Shift+Tab, ArrowUp/Down/Left/Right, Enter, Space**. Other keys are OK for their own purposes: typing, text editing, dismissal (Escape), etc.; they must not replace the core navigation/activation keys. | No mouse until demonstrably stuck. Needing mouse or **runner-requested programmatic focus** to complete an otherwise working action is a modality **failure**; record any rescue separately, never as a pass. |
| `mouse` | Pointer click, double-click, hover, wheel and drag; typing may follow pointer focus of an editable field. | Do not silently use keyboard navigation/activation or script focus to complete the pointer journey. Keyboard dismissal tests belong in the paired keyboard phase. |
| `sr-keyboard` | The `keyboard` key plan with a real screen reader running; send OS keys through Guidepup and capture speech. Reader-mode control is permitted, not a substitute for app navigation. | Same mouse/focus-rescue failures as `keyboard`. Verify focus/browse mode or VoiceOver interaction/Quick Nav state before interpreting keys. |
| `sr-navigation` | SR-specific structural navigation, reading, elements list/rotor, interaction and default-action commands; ordinary keyboard keys are also allowed. | Failed SR navigation is a **point to verify** (`review`), not automatically an app failure. Keyboard fallback can complete the step, but does not erase the review. Needing mouse or runner focus rescue is a **failure** once the barrier is demonstrated. |

These are **product modality rules**, resolving the spec's broader key allowance as recommended by its review [LOCAL]. WCAG 2.1.1 does **not** prescribe this eight-key-family restriction.

| Evidence | Verdict |
|---|---|
| Required, applicable behavior below reproducibly fails | Fail that behavior check. Attribute a WCAG failure only with criterion-specific evidence at the selected level; APG guidance alone is not normative WCAG. |
| Optional/recommended APG behavior missing | `suggestion` only; no failure merely because a shortcut is absent. |
| Mouse/focus rescue is necessary and succeeds after a demonstrated keyboard barrier | Modality `failure`; retain attempted keys, target, focus, outcome and rescue. A speculative rescue does not prove necessity. |
| Search cap, ambiguous target, unsupported command, uncertain mode/speech, reference journey also broken | `review`/incomplete/blocked, not an inferred app failure. |
| Application moves focus after opening a dialog, changing route or updating content | Not a runner violation, even when delayed. Judge the resulting focus order and user experience separately. |

## 2. Keyboard and `sr-keyboard` matrix

**Notation:** `Tab±` = Tab and Shift+Tab; `↑↓←→` = arrows. `Enter + Space` means test both independently; `Enter or Space` means the pattern permits either activation choice. `—` means no widget-specific key requirement, **not** missing coverage.

**REQUIRED** means the APG interaction for the identified variant, or the native operation to preserve. **OPTIONAL** means explicitly optional, recommended or model-dependent supplementary behavior; absence alone is a suggestion. **†** marks an APG expectation **outside the core navigation/activation policy**: inspect it in a separately labelled APG diagnostic, not as a way to pass `keyboard`/`sr-keyboard`. Home/End are *not universally optional*: sliders, trees and data grids differ from tabs/listboxes. Escape is permitted dismissal, not a core-policy exception for navigation.

For **every interactive row**, verify: a keyboard path in/out; visible, unobscured logical focus; intended postcondition; correct accessible name/role/state/value; no unexpected context change or keyboard trap. Modal containment is intentional, provided a keyboard close/exit exists. Focus can be on a roving-tabindex item **or** remain on a valid `aria-activedescendant` owner; selection is not the same as focus.

## 3. Mouse modality

Pointer checks apply to native **and** ARIA/custom controls with the same function. Read-only containers have no target-size requirement unless interactive. These checks complement, not replace, keyboard and SR runs [WCAG].

| Check / applicable patterns or roles | Required interaction / evidence | Optional / exceptions | Existing suite vs proposed |
|---|---|---|---|
| Target size: links, buttons, checkboxes/radios/switches, tabs, menu items, slider thumbs, splitter handles, media controls | Measure actual clickable area: at least **24 × 24 CSS px**, or demonstrate a 2.5.8 exception. Test adjacent hit targets, not just visual icon bounds. | Spacing exception uses centered 24px-diameter circles; equivalent control, inline, unmodified UA control, essential presentation exceptions. **44 × 44** is AAA 2.5.5, suggestion at AA. | **A:** axe `target-size`; **P:** pointer-hit/exception evidence beyond static results |
| Hover/focus content: tooltip, disclosure-like popup, menu/submenu, help/validation popover | Hover trigger → content; move pointer onto content; keep it present while trigger/content hovered; verify dismissal without moving pointer or focus (paired keyboard Escape test or accessible dismiss control). | 1.4.13 dismissibility exception for errors or content not obscuring/replacing other content; UA-controlled presentation exception. No blanket “all hover must use Escape” WCAG rule. | **M:** `tooltip-dismiss-hover`; **P:** systematic timed pointer/focus assertions |
| Hover-only essential functionality/content: menus, carousels, grid row actions, tooltips, media overlays | Reveal by pointer; separately test equivalent keyboard focus/activation route; verify content/action is available without hover. Pointer success alone cannot establish this. | Equivalent accessible route may differ visually; decorative hover styling alone is not a failure. | **M:** APG/hover review; modality helper `kbd-hover-only` is not complete proof; **P:** paired-route check |
| Pointer cancellation: all single-pointer actions, destructive buttons, sliders, drag handles | Press → move outside → release; observe whether action is aborted; inspect undo or release reversal where used. Establish allowed cancellation mechanism under 2.5.2 before failing. | Essential down-event functions excepted. | Drag alternative: sliders, multithumb slider, splitter, sortable list/tree/grid, drag/drop, carousel swipe | Perform drag, then reach same outcome using **single pointer without dragging** (e.g. click track, increment buttons, move menu). Verify comparable result, not only presence of a button. | Essential/unmodified UA behavior exceptions under 2.5.7. Keyboard-only alternative is **not sufficient** for this pointer criterion. | **M:** `drag-pointer-alternative`; **P:** outcome comparison; drag replay support must be verified |
| Multipoint/path gesture alternative: carousel swipe, zoom, drawing/gesture controls | Single-pointer, non-path-based alternative for multipoint/path-based function (2.5.1) | Essential gesture exception; distinguish true path-based gesture from dragging endpoints (2.5.7). | **M:** `drag-pointer-alternative` partially; **P:** separate gesture classification |
| Pointer activation/state: buttons, links, select/listbox, menu, tabs, disclosure, checkbox/radio/switch | Click intended target once; verify destination/state/value, disabled behavior, popup handling and no accidental adjacent activation | Double-click/context actions only if actually offered; no universal requirement for hover focus or click focus across OSes | **A:** structure/state snapshots; journey replay already clicks; **P:** explicit per-role postconditions/cancellation |
| Carousel timing; hover-revealed media controls | Hover pauses auto-rotation; content remains operable while pointer moves to controls; visible pause/stop control works | Rotation restart behavior follows carousel pattern; pause/stop obligations also depend on 2.2.2 conditions | **M:** APG/visual review; **P:** timing/state assertions |

## 4. `sr-navigation`: real-reader commands

**Required vs optional here concerns the test plan, not an author's obligation to implement SR shortcuts.** **R** = exercise one supported role-appropriate structural/reading route for in-scope content, then verify the announcement/action. **O** = alternative discovery shortcut or configuration-dependent diagnostic, absence only a suggestion/coverage note. A missing SR route produces **verify/review**, even in an R row; mouse or runner-focus dependency is a demonstrated modality **failure**. Role/name/state failures require their own reliable speech/accessibility evidence, not just a failed shortcut.

Expected spoken information is semantic, not a literal English transcript or fixed order: **N** name/text, **R** role/type, **S** state, **V** value, **P** position/context. Check only applicable parts; verbosity, locale and implicit/native semantics affect wording. Position/total may be unknown in virtualized sets. Do not require all five on every item.

### NVDA — Windows, confirmed browse mode [NVDA] [GP-N]

`NVDA` is configured Insert/numpad Insert and/or Caps Lock; resolve the actual modifier/layout. Quick-nav letters below mean **unmodified** letter, not Shift merely to spell uppercase; add Shift for previous. Native HTML headings use levels 1–6; current NVDA additionally documents levels 7–9 for ARIA/custom headings.

**Accuracy traps:** VO+Command+B searches **bold text**, not buttons; VO+Command+D finds a **different item**, not landmarks. VO+Command+N/Guidepup `nextLandmark()` searches **auto web spots**, not just ARIA landmarks. Use the Landmarks rotor to assert landmark discovery. Quick Nav toggles/assignments differ across macOS versions; the installed reader's commands/help take precedence over a memorized shortcut.

### What Guidepup can send, versus what the suite checks

| Capability | Use / limit |
|---|---|
| `sr.press(key, options)`, `sr.type(text, options)` | OS key chords/text, not Playwright targeted `locator.press()`. Resolve platform key syntax and modifiers; Guidepup does not turn a prohibited pointer/focus action into a valid keyboard action. |
| `sr.perform(sr.keyboardCommands.<name>, options)` | Documented named command mappings in [GP-N]/[GP-V]; inspect the **installed** `keyboardCommands` before use. Current public docs/source may be newer than local package. |
| `next`/`previous`, heading/link/landmark methods; `navigate…Until` | Reader-specific mappings; matching speech alone is not cursor-to-DOM identity. Bound searches and confirm role/name/context; duplicate/empty matches are inconclusive. |
| VoiceOver `commanderCommands` | Includes `ROTOR`, `ITEM_CHOOSER`, interaction/action and Quick Nav toggles. It is an alternative API surface, not proof a command is wired into the local driver. |
| `capture`, spoken phrase log, item text | Capture around each action and allow bounded settling. Existing driver uses full capture; speech log is not a guaranteed passive transcript of unrelated actions. VO item text and speech are distinct; NVDA item text reflects speech. |
| `click()` and mouse-routing commands | **Pointer input**, despite being exposed by an SR library: banned outside recorded rescue under keyboard/SR modalities. Likewise do not silently use runner focus or cursor-routing APIs to manufacture reachability. |
| Existing suite | Generic OS-key replay, heading/landmark/linear sweeps and **S** heuristics exist in [reader drivers](skills/screen-reader-validation/scripts/lib/drivers). Full quick-nav-by-role, elements-list/rotor assertions and robust mode-state handling are **proposed**, not established merely because Guidepup exposes the command. Mock/DOM sweeps do not validate actual speech or reader navigation. |

| Observation in either reader | `verify` / failure boundary |
|---|---|
| Structural quick-nav/rotor route misses target, ordinary keyboard reaches it | `review` (`srnav-not-reachable`/semantic-nav review): include reader/browser/version, mode, commands, speech, target role/name/context and fallback. |
| Missing speech, unsupported command, unknown foreground/mode, disabled rotor category, ambiguous cursor identity | Coverage/setup `review`; do not claim missing name/role/landmark or app failure. |
| Reliable, aligned capture shows missing control name/role/state/value or unannounced status/error | Apply the appropriate **S** rule and WCAG evidence threshold. Silence alone is not always an error: redundant/unmodified state or verbosity settings can explain it. |
| Reader commands and keyboard fallback demonstrably cannot complete action; mouse/focus rescue succeeds and is necessary | Modality **failure**, with rescue distinguished from independent semantic/speech finding. App-managed focus is not rescue. |

## 5. Detect → key plan

| Detect / establish | Plan | Observe before deciding |
|---|---|---|
| Native element/type, computed accessibility role/name, ancestor pattern, orientation, popup role, disabled/read-only state | Prefer native key behavior; combine container navigation with child activation; never choose Enter/Space interchangeably for every role | Actual user-facing function and state; role alone does not implement behavior. Native disabled ≠ `aria-disabled` behavior automatically implemented. |
| Plain link / button / checkbox / switch | Reach by Tab±; Enter for link; test Enter and Space for button; Space for checkbox/switch | Target-specific navigation/action/checked/pressed transition; no double activation |
| Composite with roving tabindex / active descendant | Tab into owner/active item; orientation-correct arrows; role-specific activation; Tab out | Deep DOM focus **or resolved active descendant** and popup relationship; merely owning/controlling target does not prove target is active |
| Combobox or popup-bearing trigger | Open with applicable core key; branch on **listbox/grid/tree/dialog**, not a generic popup algorithm | Expanded state, actual active item/value, popup focus model and close/return |
| Modal dialog / non-modal overlay | Modal: observe app's initial focus, cycle Tab±, dismiss and restore. Non-modal: verify an appropriate reachable route without demanding trapping | No forced runner focus to establish the “correct” start; initial focus may be static text; `aria-modal` alone does not make background inert |
| Editable / native picker / editor | Reach naturally; confirm text/focus mode; type/edit; use actual picker/editor model | Caret/value changes versus SR cursor changes; preserve user data; explicitly mark OS-dialog/UA observation limits |
| Static heading/list/table/landmark/meter | No fabricated widget keys or mandatory Tab stops; `sr-navigation` semantic route | Accessibility structure, text/header/value/context; non-focusable does not mean inaccessible |
| `sr-navigation` target | Confirm foreground and reader navigation state; choose role-specific route in §4; then keyboard fallback if needed | Record SR miss as review; don't infer virtual cursor identity from `document.activeElement` alone |
| APG required † or optional shortcut | Run only as separately labelled APG diagnostic, if safe; never use it to erase a restricted-core barrier | Exact APG variant/conditional requirement, and whether a real WCAG functional barrier exists |
| No progress after valid pattern plan | Reverse/exit where applicable; distinguish complete search from cap/virtualization/delay; use safe reference/reset before rescue | Reproducible barrier and success oracle. Reference journey also fails → blocked; optional rescue disabled → inconclusive, not presumed failure |

**Caveats**

- **Modes:** NVDA browse arrows read, focus arrows can alter a field; NVDA+Space is a toggle, Escape is not an unconditional mode reset. VoiceOver has interaction depth/Quick Nav, not NVDA's identical browse/focus model. Never run destructive “probe” keys while state is unknown.
- **Autofocus:** record initial target and reader state before any key. Autofocus is app behavior, not proof of keyboard failure; review unwanted focus/context loss and unsafe starting mode. Do not silently blur/focus elsewhere to make probes pass.
- **Application focus management:** dialog/route-heading focus and delayed focus restoration may be necessary accessibility features. Only **runner intervention required for progress** is the modality focus failure.
- **Evidence:** use a meaningful per-step before/after postcondition, bounded settling and safe resettable data. Unrelated mutation/network activity is not proof of activation. Do not try another activation merely because success was silent; it can submit twice.
- **Boundaries:** frames, shadow roots, virtualized sets, native OS dialogs, localization and reader/browser settings can limit observations. Mark uncertainty explicitly; an exhausted search is not proof of an unreachable control.
