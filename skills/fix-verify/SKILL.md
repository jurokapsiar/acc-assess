# Fix Verify

Companion to the **accessibility-assessment** skill. Given one or more `fix-*.md` files it
generated, re-run the same checks against the app with the fix applied, and decide
`fixed | not fixed | regressed | unverified | needs review` with proof screenshots — not a
guess, a replay of the original plan against the live page.

## Prerequisites

- The **accessibility-assessment** skill installed as a sibling folder (`../accessibility-assessment`
  relative to this skill), with its dependencies installed (`npm run setup` there) — `verify.mjs`
  and its shared `node_modules` live there; this skill has no engine of its own.
- The target app **running with the fix already applied** (same `baseUrl` the baseline
  assessment used). This skill only verifies: it never edits source, applies or reverts a fix.
  Applying a fix file's **Changes** is done by the user or a separate skill, before this one runs.
  If the fix was applied in a copy, branch or worktree served at the same `baseUrl`, still run
  `verify.mjs` from the original app root (where `.a11y/` lives).
- The **same inventory** (`.a11y/inventory.json`) the baseline run used — if screens or locators
  changed since, see Troubleshooting. If the fix renames a control an inventory step clicks, change
  that locator to a `"/regex/"` name matching both names and verify with `--accept-plan-change`.

## Input

One or more `fix-*.md` files (one per rule + component, so each covers related elements and
verifies on its own), found in a `.a11y/reports/<timestamp>/` run directory (generated by
`fixes.mjs`, see the accessibility-assessment skill's SKILL.md Step 4). A `draft` fix file can
still be verified — useful as a quick "is it actually fixed" check — but its status badge and
missing `changes` entry are reported as-is; point that out to the user rather than treating a
draft the same as a reviewed fix.

## Workflow

1. **Read the fix file.** Its trailing `a11y-verify` JSON code block names the issue, rule, WCAG
   criterion and exactly which targets/nodes are being verified. The Markdown body above it has
   the human-readable occurrences, repro steps and (if reviewed) the proposed change.
2. **Run the verifier:**
   ```bash
   node <accessibility-assessment-skill-dir>/scripts/verify.mjs <fix-file.md...> [--quick] [--accept-plan-change] [--channel c] [--headed] [--workers n]
   ```
   Run from the app root, same convention as `assess.mjs`. This re-runs `assess.mjs` against just
   the fix file's targets, relocates every listed node in the live page, appends an attempt to
   `<run>/fix-report.json`, and renders `<run>/fix-report.html`. One status line is printed per
   fix file. A full re-run takes about as long as the baseline for those targets (minutes for
   dozens of targets); `--quick` re-runs only the issue's own check plus the checks it depends on
   (axe → axe; abledom → abledom + keyboard; keyboard → keyboard + overlay). `fix-report.html`'s
   Fixes section lists every fix file the run's `fixes-manifest.json` currently knows about (not
   just the ones verified so far), each with its rule/component, `ready`/`draft` status, and a
   verification status of `fixed` / `not fixed` / `regressed` / `unverified` / `needs review` for
   an attempted file, or `not yet verified` for one `verify.mjs` hasn't been run on yet; the
   per-attempt proof detail (occurrences, criteria, regressions) still only renders for files
   that have an actual attempt. Re-running `verify.mjs` on more fix files only ever appends new
   attempts — earlier ones are never dropped or overwritten. The re-run stops
   starting new targets as soon as one can't be reached, since the attempt is `unverified` anyway.
   If the baseline was a scoped run (`skills/scope-definition`, `assess.mjs --scope`), the same
   scope file is forwarded to the re-run automatically — nothing to pass here. If that scope
   file is missing, the attempt is `unverified (scope file not found)` rather than silently
   falling back to the bare inventory; restore the file or re-baseline. For a `needs review`
   manual replay (step 3), prefer `scope.mjs replay --scope <f> --target <key> --headed` (read-only,
   opens the browser at the target state) over ad-hoc re-navigation when the target came from a
   scope.
3. **For any `needs review` result** (a `review`-kind issue, or one from agent judgement, not an
   engine rule — these can never auto-resolve to `fixed`): replay the fix file's **Reproduce**
   steps with Playwright, compare the before screenshot against the live page now, and decide.
   Write `<run>/verify/<timestamp>/agent-verdicts.json`:
   ```jsonc
   { "<issue>": { "status": "fixed", "note": "Tab now reaches the close button; Escape closes the menu." } }
   ```
   `<issue>` is the fix file's `issue` field (`"<kind>:<source>:<rule>[@<file>[#<component>]]"`). Then re-render without
   re-running checks:
   ```bash
   node <accessibility-assessment-skill-dir>/scripts/verify.mjs --render-only <run>
   ```
4. **For any `unverified` result**, follow the printed reason:
   - *incompatible config* (engine version, level, viewport size or a target's plan changed) —
     the baseline is stale. Re-run `assess.mjs` to get a fresh baseline and fix file, or, if only
     an inventory step's label changed (not its meaning), re-run `verify.mjs` with
     `--accept-plan-change`.
   - *target not reached* / *check "X" did not complete* — fix whatever broke the plan (see the
     accessibility-assessment skill's inventory troubleshooting), then re-verify. Every check
     that completed at baseline must complete again on the affected targets, not only the
     issue's own check.
   - *node unresolved* — the element's selector/class changed and it has no role+name or source
     line strong enough to relocate it. Add a stable locator (role + accessible name) to the
     inventory, or re-baseline with a fresh `assess.mjs` run if the element genuinely changed.
   - *modality evidence gap* — a `kbd-*` fix is verified by re-running the same modality; if that
     run was blocked/partial or the step was skipped/inconclusive, the absence of a finding is
     not proof. Re-run with a higher `--max-presses`, or confirm the step manually.
   - *not a fresh browser context* — the verification run used `--setup` with a non-fresh
     isolation, `--cdp`, or recorded interventions (`results.execution`). That can't prove a
     fix; re-run `verify.mjs` without them, or confirm manually. `verify.mjs` forwards
     `--setup`/`--cdp` to the assessment subprocess.
   - Findings the agent marked *potentially out of scope* never count as regressions.
5. **Summarise to the user** (`node <accessibility-assessment-skill-dir>/scripts/summary.mjs <run>` lists the run's fix files and their status): how many fixed / not fixed / regressed / needs review / unverified,
   one line per issue with its reason, and the `fix-report.html` path.

## Exit codes (`verify.mjs`)

| Code | Meaning |
|---|---|
| `0` | All given fix files verified `fixed` |
| `1` | At least one `not fixed` or `regressed` |
| `2` | At least one `unverified` or `needs review`, and none at exit `1` |
| `3` | Usage error (bad arguments, fix file not found or malformed) |

`--render-only <run>` always exits `0` (it only re-renders `fix-report.html` from the existing
`fix-report.json` plus any `agent-verdicts.json`).

## Version policy

A fix is only verified against a compatible baseline. **Hard-fails** (`unverified (incompatible:
<field>)`) on a mismatch: `axe-core`, `abledom`, `level`, any listed viewport size, or a target's
`planHash` or execution policy (step modalities, intent, keys, skips), unless `--accept-plan-change`. **Warning only** (the attempt still proceeds):
Playwright version and the inventory file's checksum (edits that change a target's steps show up
as `planHash` changes). The knowledge snapshot isn't compared. Full decision rules:
[references/decisions.md](references/decisions.md).

## Troubleshooting

| Problem | Fix |
|---|---|
| `verify.mjs` can't find `assess.mjs` | Confirm the sibling path: this skill assumes `../accessibility-assessment` next to it, with `npm run setup` already run there |
| Every attempt comes back `unverified (incompatible: axe-core)` or similar | A dependency was upgraded in the accessibility-assessment skill since the baseline ran. Re-run `assess.mjs` for a fresh baseline |
| `unverified: target not reached` right after the fix | The app isn't serving the fix yet (stale dev server / build cache) — confirm the change is live at the inventory's `baseUrl` before verifying. Or the fix renamed a control a plan step clicks: use a regex name in the inventory and `--accept-plan-change` |
| Warning `inventory sha256 differs` | The inventory was edited since the baseline. Harmless unless a target's steps changed, which fails as a `planHash` change |
| `regressed` on an unrelated rule | The fix changed shared markup/CSS. Check the listed regression(s) in `fix-report.html` before assuming the original fix is wrong |
| Same issue stuck at `needs review` after writing `agent-verdicts.json` | Confirm the JSON key matches the fix file's `issue` field exactly, and that you re-ran with `--render-only <run>` (the same run directory as `report.html`) |
| `unverified: scope file not found` | The baseline was a scoped run (`assess.mjs --scope`) and the scope file it points to is gone. Restore it, or re-baseline with the sibling `skills/scope-definition` skill's current scope |
