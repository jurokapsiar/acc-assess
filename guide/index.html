WCAG 2.2 + WAI-ARIA APG

Accessibility-assess skills

A set of skills that validate accessibility based on user journeys, using deterministic tools and agents. axe-core static analysis, AbleDOM real-time analysis and WAI-ARIA APG pattern review against WCAG 2.2 combine into a comprehensive analysis.

It still does not replace manual testing. It aims to make manual testing more accurate. Research phase: no evals yet, and validated with few models so far.

01

Install

Four Agent Skills plus a Claude Code plugin wrapper. Install all four together: the companion skills load Playwright and shared code from accessibility-assessment. Needs Node.js 20+, npm, and network access on first setup.

Option 1 · skills CLI

recommended

Vercel's skills CLI installs into the native skill folders of Claude Code, Cursor, Codex, GitHub Copilot, Gemini CLI, Antigravity and more. Omit --global for a project install; add --agent claude-code cursor to pick agents.

npx skills add jurokapsiar/acc-assess --skill '*' --global --yes
cd ~/.agents/skills/accessibility-assessment   # or the path the CLI printed
npm run setup

Option 2 · Claude Code plugin

auto-updates

Setup is automatic: a background SessionStart hook installs whatever is missing in the installed plugin copy, and again after each plugin update. Skills are namespaced, e.g. /acc-assess:accessibility-assessment.

/plugin marketplace add jurokapsiar/acc-assess
/plugin install acc-assess@acc-assess

Option 3 · Other agents

manual

Copy all four skills/*/ folders, side by side, into the agent's documented skill directory, then run setup in accessibility-assessment/.

cp -r skills/* <agent-skills-dir>/
cd <agent-skills-dir>/accessibility-assessment
npm run setup

Option 4 · Release download

planned

A GitHub Action will publish a skills/ zip with every version tag (tests and plugin validation first). Until the first release, download the repository ZIP from GitHub and copy the four skills/*/ folders as in option 3.

cd ~/.claude/skills/accessibility-assessment
npm run setup

Research phase. The skills still lack evals and validation across models. Agentic review does not replace user testing. npm run setup is idempotent: it installs only what is missing (npm deps, Playwright Chromium, the WCAG 2.2 + APG knowledge cache), and npm run setup:check prints ready when done.

02

Workflow

Seven steps, four skills. Each step writes a file the next step reads, so you can stop, inspect and resume.

  1. Define the scope

    you approve

    Describe what to test in plain words. The skill turns it into screens, states and user journeys and asks you to approve them.

    node scripts/scope.mjs init --prompt "New task flow and settings" --url http://localhost:3000
    Skill: scope-definitionWrites: scope.json journeys.json

  2. Discover the inventory

    skill

    Features, screens and states are discovered and checked against the scope, so nothing in scope is skipped silently.

    node scripts/inventory.mjs validate
node scripts/inventory.mjs verify
    Skill: accessibility-assessmentWrites: inventory.json

  3. Assess

    skill

    Every screen and state at each viewport: axe-core, AbleDOM, and Playwright checks such as keyboard walk, overlays, 320px reflow and text spacing.

    node scripts/assess.mjs --scope .a11y/scope.json
    Skill: accessibility-assessmentWrites: results.json screenshots

  4. Review and report

    skill + agent

    The agent reviews what tools cannot decide and records its judgement. The report groups failures, items to review and suggestions.

    node scripts/report.mjs
    Skill: accessibility-assessmentWrites: report.html

  5. Write fix files

    code edit out of scope

    One Markdown file per issue: the fix, the changes, the occurrences, repro steps and a verify command. Applying the change is out of scope due to code base specifics.

    node scripts/fixes.mjs
    Skill: accessibility-assessmentWrites: fix-*.md

  6. Verify the fix

    skill

    Re-runs each fix file against the changed app and proves it with before/after crops of every occurrence.

    node scripts/verify.mjs .a11y/fixes/fix-*.md
    Skill: fix-verifyWrites: fix-report.html exit 0 · 1 · 2 · 3

  7. Validate with a screen reader

    skill

    Drives NVDA (Windows) or VoiceOver (macOS) through the same journeys with Guidepup and checks what is actually announced.

    node scripts/sr.mjs preflight
node scripts/sr.mjs run --scope .a11y/scope.json
node scripts/sr.mjs analyse && node scripts/sr.mjs report
    Skill: screen-reader-validationWrites: sr-report.html

The skills never edit your source code. They read, run and report. Fixes are proposals in fix-*.md. Editing code is out of scope due to code base specifics; apply them with your own process, then fix-verify proves the result.

03

The skills

Ask in plain language. Each skill knows its scripts and hands off to the next.

scope-definition

Turns a sentence into an approved, reproducible test scope.

  • Screens, states and viewports from your prompt
  • User journeys as replayable steps
  • Pause for human approval before any assessment

Assess the checkout flow on mobile and desktop.

Output: scope.json, journeys.json

accessibility-assessment

Runs the tools, adds agent review, and writes the report and fix files.

  • axe-core, AbleDOM and Playwright checks per state
  • Agent judgement for what tools cannot decide
  • One fix file per issue, with repro and verify command

Run an accessibility assessment of the approved scope.

Output: report.html, fix-*.md

fix-verify

Proves that an applied fix worked, without new regressions.

  • Re-runs only what the fix file names
  • Before/after crops for every occurrence
  • Status: fixed, not fixed, regressed, unverified, needs review

Verify the fixes I just applied.

Output: fix-report.html

screen-reader-validation

Listens to real NVDA or VoiceOver output for each journey.

  • Guidepup drives the reader with OS-level keys
  • Session log: step, keys, what was heard
  • Silent, missing or wrong announcements become issues

Check the new-task journey with NVDA.

Output: sr-report.html

Run with --modality keyboard,mouse (assessment) or --modality sr-keyboard,sr-navigation (screen reader); all runs both of a skill's phases. Each modality is a separate replay in a fresh browser. Journeys without modalities keep the default behaviour.

When the keyboard gets stuck: the escalation ladder

The runner climbs only as far as needed, records each rung, and keeps going.

  1. rung 0Core keysTab Shift+Tab ↑ ↓ ← → Enter Space
    no issue
  2. rung 1Other keysEsc Home End F6 or a documented shortcut
    kbd-nonstandard-key · suggestion
  3. rung 2Programmatic focusThe runner had to call focus()
    kbd-programmatic-focus · failure
  4. rung 3MouseOnly a click got through
    kbd-mouse-required · failure
  5. rung 4Give upThe journey is reported as partial
    partial journey

05

The reports

Static HTML that opens from disk. Every finding links to a screen, a state, a viewport, a crop and a source line.

Summary

  1. Issues by severityFailures as a half-donut, split by impact.
  2. CriteriaCriteria with issues, needing review, or with nothing detected. Never "pass": tools can only fail to find problems.
  3. Screens with issuesHow many scoped screens have at least one failure.
  4. IssuesConfirmed failures, grouped by rule.
  5. Needs reviewTool results that need judgement, and agent findings.
  6. ScreensThumbnails jump to every state assessed.

Issue card

  1. ChipsKind, impact, WCAG criterion and the rule that found it.
  2. FixWhat to change, in plain words, with the affected files.
  3. SourceFile and line resolved from the rendered element.
  4. OccurrenceScreen, state and viewport. Steps to reproduce are one click away.
  5. Element cropThe failing element, outlined on the real screenshot.

Report sections

Each section has its own tint, used in the title row of every box.

Criteria

Each criterion with its status and the rules behind it.

Needs review

Items a tool could not decide, with the agent’s note.

Scope

What was assessed, and what was not.

User journeys

Each journey, step by step, with its outcome.

Fix-verify report

Fixed, not fixed, regressed, unverified or needs review, for each fix file.

Verification status

Exit code 0 when all fixed; 1, 2 or 3 otherwise.

Proof

Before and after, element by element.

Screen-reader report

Real NVDA or VoiceOver output, step by step.

Summary

Issues and how many steps produced speech.

Finding

What was heard, what was expected, and the fix.

06

Example issues

One from each assessor. Every issue carries the evidence, the steps to reproduce it and a fix you can apply.

Accessible name does not contain the visible label

  • axe-core
  • failure
  • serious
  • SC 2.5.3
  • label-content-name-mismatch

A date button shows “Tuesday, November 3” but its accessible name is “Change task date”. Speech-input users who say what they see can’t activate it.

Steps to reproduce

  1. Open the app at 1280×800.
  2. Select New task.
  3. Inspect the date button in the dialog.
  4. Compare its visible text with its accessible name.
Fix

Start the accessible name with the visible text.

- <button aria-label="Change task date">Tuesday, November 3</button>+ <button aria-label="Tuesday, November 3, change date">Tuesday, November 3</button>

Toggle field name needs a check

  • axe-core
  • review
  • serious
  • SC 4.1.2
  • aria-toggle-field-name

axe-core can’t tell if a wrapping label names a role="switch". The agent checks each occurrence and records the result; mismatches become their own finding.

Steps to reproduce

  1. Open the switch demo at 1280×800.
  2. Inspect each switch.
  3. Compare the label text with the computed name.
Fix

Keep aria-label equal to the visible label, or reference it with aria-labelledby.

+ <span role="switch" aria-labelledby="lbl-apca" aria-checked="true">

Tab order does not follow reading order

  • agent
  • review
  • SC 1.3.2, 2.4.3
  • tab-order-reading-order

The keyboard walk is overlaid on the screenshot as numbered stops. The agent compares that order with the visual layout.

Steps to reproduce

  1. Open the screen at 1280×800.
  2. Press Tab from the top of the page.
  3. Follow the numbered stops.
Fix

Make DOM order match visual order. Avoid positive tabindex and CSS-only reordering.

Navigation produced no announcement

  • Guidepup
  • review
  • moderate
  • SC 2.4.3
  • sr-silent-navigation

After a route change the screen reader said nothing, so the user can’t tell where they are.

Heard
(nothing)
Expected
The new page title or heading

Steps to reproduce

  1. Start NVDA.
  2. Run the journey with sr.mjs run.
  3. Activate the link that changes the view.
  4. Listen.
Fix

Give every page/view a unique <title> and move focus to the new view's heading (or announce the route change).

Step can only be completed with a mouse

  • Playwright
  • failure
  • critical
  • SC 2.1.1
  • kbd-mouse-required
  • modality keyboard

In the keyboard phase the runner climbed the escalation ladder; only a pointer click completed the step.

Steps to reproduce

  1. Run the journey with --modality keyboard.
  2. Tab to the control.
  3. Press Enter or Space.
Fix

Make the control operable from the keyboard: use a native button/link/input, or add tabindex="0" with Enter/Space handlers and a matching role.

- <div class="add" onClick={add}>Add item</div>+ <button type="button" onClick={add}>Add item</button>

Escalation trace

step 3  intent: activate  target: "Add item"
  rung 0  Tab ×14, Enter, Space   → not reached
  rung 1  Escape, Home, End        → not reached
  rung 2  programmatic focus()     → focused, Enter ignored
  rung 3  mouse click              → completed
  stuck: no-activation   focus came from: programmatic
